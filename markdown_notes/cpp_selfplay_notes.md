- Engine: ~1.3M moves/s/core (random playouts, full legal-gen incl. BFS).

## Wall-legality optimization (engine.hpp, validated)
- Added `h_wall_contacts()`/`v_wall_contacts()` (~line 296-344): O(1) contact-point count at a candidate wall's endpoints. If contacts < 2, wall is legal unconditionally (no BFS needed) even if it crosses the cached shortest path — this is Grant Slatton's contact-counting rule, complementary (not redundant) with the existing path-edge-set heuristic. Gated into `gen_legal()` as an extra AND condition before running `reach()`.
- Validated via tests/test_cpp_parity.py (2000 games/541k moves, zero mismatches). Benchmarked via `random_playouts`: ~1.27x (5x5), ~1.70x (7x7), ~2.1x (9x9/10walls) speedup vs pre-optimization baseline.

## Transposition-table feasibility (measured, not yet implemented)
- num_threads_ (small, core-bound, e.g. 8) is decoupled from parallel_games_ (100+) — games multiplex over a small worker pool via a shared `ready_` deque + one mutex (`mu_`). A shared cache would only see ~8-way contention, not 100+-way — much more tractable than it first appears.
- Real bottleneck to cache is NN inference (GPU round-trip via get_batch/put_results), not gen_legal (already fast). Cache should map state hash → (policy, value) NN output, not legal-move lists.
- `Node` struct has `prior` vs `base_prior` split — Dirichlet noise applied post-lookup at each game's own root, so NN-output caching is orthogonal/compatible with per-game root noise.
- Added diagnostic instrumentation (kept in repo) to measure this empirically instead of guessing:
  - `Game::opening_hashes` / `kOpeningTrack` (selfplay.hpp) — records post-move Zobrist hash for first N real plies per game.
  - `SelfPlayManager::get_openings()` + `.def("get_openings", ...)` in bindings.cpp — drains (n_games, kOpeningTrack) hash array + lengths.
  - `tools/_measure_opening_overlap.py` — runs real production self-play (real MCTS/noise/temp) capped at `--depth` plies, groups games by move-hash prefix, reports distinct-state count / hit-rate per depth.
- **Measured result (runs/models_7x7_v2/best.pt, 800 games, 7x7/5walls, sims=64):** hit-rate (fraction of games whose position at that depth was already seen by an earlier game) decays smoothly, NOT a cliff: depth1 95%, depth4 84%, depth8 55%, depth10 34%, depth12 17%, depth16 ~6% (noise floor).
- **Fresh/untrained network is completely different:** hit-rate collapses to 0% by depth 4 (policy is near-uniform, no convergence onto shared lines yet). This means the "worthwhile depth" is NOT a fixed property of the game — it depends heavily on how converged the current network is. Early training cycles: cache only helps to ~depth 2-3. Late/converged cycles: real value out to ~depth 10-12.
- Conclusion: depth-0 root should be an explicit one-off precompute (frozen, no locks — literally 1 state per cycle). Depths 1+ should be an ordinary shared, depth-capped cache filled *organically* during self-play (not a separately-built "opening book" — a static book would go stale as the policy converges further and can't adapt to the shifting hit-rate profile the way organic fill does for free). Recommended default depth cap ~8-12 (err generous — a wasted cache slot costs nanoseconds, a missed cacheable hit costs a full NN round trip). Re-run `tools/_measure_opening_overlap.py` periodically across training to sanity-check the cutoff still makes sense as the policy evolves.

## Shared transposition table (IMPLEMENTED + validated + benchmarked)
- `Config::tt_max_depth` (default 8, negative disables) — caches states with `st.depth <= tt_max_depth`.
- Key = `TTKey{zhash, packed(walls_p1,walls_p2)}` — zhash alone is UNSAFE because walls_p1/walls_p2 (remaining wall budgets) are separate NN input planes not encoded in zhash; two different histories can reach the same zhash with different wall budgets.
- Value cached = RAW (unmasked) NN logits (full action space) + scalar value — NEVER cache `legal` (repetition-avoidance via `RepCounter` makes legal move sets history-dependent even for identical zhash+walls). `legal` is always freshly recomputed per lookup; `masked_softmax(row, legal, priors)` renormalizes cached logits against the current legal set. This makes the cache correctness-safe regardless of path/history differences.
- Storage: manager-level, sharded (`kTTShards = 64`) `unordered_map<TTKey, TTEntry, TTKeyHash>` each behind its own `std::mutex`, shared across all parallel games. Cleared on every `start()` call (TT validity is tied to fixed NN weights for that run).
- Control flow: `gather()` checks cache before building NN input planes (skips `nn_input()` entirely on hit); `submit_root()` returns bool (false = cache hit, integrate immediately); `submit_pending()` only enqueues unresolved leaves; `put_results()` inserts into cache for `cacheable` leaves after a real NN eval.
- Exposed via pybind11 constructor `tt_max_depth` (default 8) and `selfplay_cpp.py --tt-max-depth` CLI flag.
- **Correctness validation:** ran identical seed/settings (7x7/5walls, sims=64, 128 parallel, 8 threads, runs/models_7x7_v2/best.pt) with `--tt-max-depth -1` vs `8` at both 300 and 800 games — win/loss/draw counts, mean plies, mean walls, and position counts were **bit-identical** between runs. Confirms the TT is a pure speed optimization with zero behavioral change (cached NN outputs are exact copies of what a live forward pass would have produced for that exact state).
- **Speed benchmark (M1 Air, 800 games, 7x7/5walls, sims=64, 128 parallel/8 threads, runs/models_7x7_v2/best.pt, seed=42):**
  - TT disabled (`-1`): 61.3s → 46,967 games/hour; 1,043,013 NN evals (17,009 evals/s, mean batch 203.2).
  - TT enabled (`8`, default): 54.9s → 52,468 games/hour; 877,028 NN evals (15,978 evals/s, mean batch 195.4).
  - TT enabled (`12`): 49.1s → 58,701 games/hour; 769,929 NN evals (15,693 evals/s, mean batch 190.1).
  - depth 8 vs disabled: **~11.7% faster, ~15.9% fewer evals**. depth 12 vs disabled: **~24.9% faster, ~26.2% fewer evals**. depth 12 vs depth 8: ~11.8% faster still — deeper cap kept paying off, no sign of diminishing returns yet at 12 (matches measured hit-rates of 17-43% for depths 9-12, well above the ~6% noise floor at depth 16). Win/draw/ply stats were bit-identical across all three runs (235/549/16, mean plies 42.0, walls/game 8.2) — confirms correctness holds at depth 12 too.
  - Note: this is on the M1 Air exploration machine only — expect a different absolute ratio on the target Ryzen+RTX5070Ti box, but the *mechanism* (cache absorbs a fixed fraction of shallow-depth NN calls) should transfer. Worth trying `tt_max_depth` even higher than 12 on the target machine given no diminishing returns observed yet at this depth.

## TT stress test with fresh/untrained network (no crash, but watch reproducibility expectations)
- Ran `selfplay_cpp.py` with no `--model` (fresh random net), 800 games, 7x7/5walls, sims=64, seed=42, at `tt_max_depth -1` and `16`: no crash/hang either way; TT enabled was even slightly faster (69,913 vs ~64,400-38,527 games/hour).
- **Important caveat discovered:** with a fresh/random network, re-running the exact same TT-**disabled** config twice with the same seed gave completely different results (P1/P2/draws 9/743/48 vs 20/594/186, 21,987 vs 37,112 positions, 44.7s vs 74.8s). This is pre-existing non-determinism in the concurrent MPS batched-inference pipeline (thread scheduling → different batch compositions → tiny FP differences), NOT something the TT introduced. A random/untrained policy has noise-level score margins, so tiny FP differences flip argmax/sampling choices and compound over long games. With a trained model this same non-determinism exists but never matters (real policy margins dwarf FP noise) — hence why trained-model TT on/off comparisons were bit-identical but random-model ones are not. Don't use a random/fresh network to test TT correctness via output-matching; use a trained checkpoint instead (as done in the validated benchmark above).

## TT eviction policy (IMPLEMENTED + validated + benchmarked)
- Problem: TT had no eviction — a strictly-growing per-shard `unordered_map` for the life of one process, bounded only by `tt_max_depth` gating eligibility (and `st.depth` = real+simulated depth, so raising the cap toward `max_moves` makes ~every simulated leaf in every tree eligible — real risk of unbounded memory on a long/large production run, even though a single 800-game test run didn't expose it).
- Fix: `Config::tt_max_entries` (default 2,000,000 total, 0 = uncapped) split evenly across `kTTShards`. In `tt_insert()`, only a genuinely-new key can grow a shard; if the shard is at its per-shard cap, evict an arbitrary entry (`shard.map.erase(shard.map.begin())`, O(1), no LRU bookkeeping/extra locking on the hot lookup path) before inserting. Overwrites of an existing key never trigger eviction. Eviction can't cause incorrect behavior — an evicted key just becomes a normal cache miss (live NN eval) next time.
- Exposed via pybind11 `tt_max_entries` arg and `selfplay_cpp.py --tt-max-entries`.
- **Validated:** forced heavy churn (`tt_max_entries=640`, `tt_max_depth=200`, i.e. cache-everything-eligible with a tiny cap) still gave bit-identical results (positions/win/draw/ply counts) vs every uncapped run — confirms eviction is correctness-safe even under constant churn.
- **Benchmark (M1 Air, 800 games, 7x7/5walls, sims=64, 128 parallel/8 threads, runs/models_7x7_v2/best.pt, seed=42):** `tt_max_depth=200` (cache virtually everything) + `tt_max_entries=50000`: 39.0s → **73,931 games/hour**, 553,152 evals, peak memory 2.21GB — beats every smaller-depth config (depth 12 was 58,701 games/hour/769,929 evals) while keeping memory in the same ballpark as TT-disabled (2.17GB peak). Win/loss/ply stats bit-identical to every other run at this seed (235/549/16, mean plies 42.0, walls/game 8.2).
- **Repeatability confirmed:** re-ran the same depth=200/cap=50000 config 2 more times — 39.7s (72,626 games/hour) and 39.8s (72,336 games/hour), evals 553,515 / 553,563. Consistent (~39-40s / ~72-74k games/hour), not a one-off fluke; win/loss/ply stats identical across all three runs.
- **Practical takeaway:** the entry cap is what makes it safe to set `tt_max_depth` very high (even to `max_moves`) — depth no longer needs to be conservative once the cap bounds worst-case memory.
- **IMPORTANT — cap=50,000 is too small and actively hurts speed at this test's scale (800 games, 7x7/5walls, seed=42, depth=200):** it caused constant eviction/thrashing (entries evicted while still needed → re-computed as fresh NN evals). Measured: cap=50,000 → 39.0-39.8s, ~553k evals, 2.21GB peak. cap=2,000,000 (default, effectively no eviction at this scale) → **22.8-24.0s (~2x faster!), only ~257k evals, 2.29GB peak** — nearly identical memory cost since neither run saturates either cap. Win/loss/ply stats bit-identical across all cap values (235/549/16, mean plies 42.0, 33,640 positions) — correctness unaffected by cap size, only speed.
- **Revised recommendation: keep `tt_max_entries` at the default (2,000,000) or higher, NOT tightened to something like 50k** — the cap doesn't cost memory unless the table actually fills up to it, so a generous cap is "free" until a run is large/long enough to approach it. Only lower the cap if a long production run is observed to actually run low on RAM. Depth can be pushed to `max_moves` (200) with the generous cap.
- **Cap sweep above 2M (same 800-game/seed=42/depth=200 test) — confirms a plateau, not a wall**: cap=2,000,000 → 22.8-24.0s/~256.8-257k evals; cap=5,000,000 → 23.0s/256,834 evals; cap=0 (fully uncapped) → 23.0s/256,914 evals. All bit-identical stats (235/549/16, 33,640 positions). Raising the cap above ~2M buys nothing at this scale because the actual working set of distinct cacheable states (~257k) never gets anywhere near 2M — there's nothing left to evict either way. This is a workload-size-dependent plateau, not evidence that 2M is some universal magic number; a much larger/longer production run (more games, more parallel, higher sims, bigger board) would have a bigger working set and could benefit from (or need) a higher cap. Always re-sweep if scale changes significantly.

## Target production self-play parameters (IMPORTANT — use these for sweeps, not the 64-sims smoke-test config)
- The 64-sims/128-parallel/leaf_batch=8 configs used throughout most of the benchmarking above were quick smoke tests, NOT representative of real training cycles. The actual self-play cycles will run something very close to:
  `--sims 800 --parallel 1024 --leaf-batch 1 --max-batch 256 --threads 8 --boardsize 7 --walls 5 --tt-max-depth -1 --tt-max-entries 20000000` (or similar order-of-magnitude cap).
- **Always prefer sweeping/tuning at (or near) these realistic params** rather than the smaller 64-sims numbers — throughput ratios, TT cap "sweet spots", and batch-size behavior all depend on scale (more sims = deeper/more simulated-tree TT eligibility per move; more parallel games = bigger working set of distinct cacheable states per unit time; leaf_batch=1 vs 8 changes how batches are assembled). Conclusions drawn at sims=64 do NOT necessarily transfer to sims=800 configs.
- **`max_batch=256` above is NOT a tuned/settled value** — it's just what the M1 sanity check happened to use. On the target RTX 5070 Ti (far more compute/memory than M1's integrated GPU, and this model is small so kernel-launch overhead matters more), a bigger max_batch likely helps further. `TARGET_MACHINE_BENCHMARK_PLAN.md` step 4 now includes higher max_batch (1024) and parallel (2048) combos in its sweep grid specifically to test this — don't assume 256/512 is a ceiling on the target machine; use whatever step 4 actually finds as the winner for all later steps/sweeps (including 4a's TT cap sweep).
- **`leaf_batch` is fixed at 1 for all throughput/TT-cap tuning (step 4 and 4a)** — batching multiple leaves per simulation is a search-quality tradeoff (batched leaves get evaluated against stale virtual-loss stats, not a fully backed-up tree), not a free speed knob like `parallel`/`max_batch`, so it shouldn't be conflated with pure throughput sweeps. Parallel games alone already give the GPU plenty of batching opportunity without touching leaf_batch. Whether leaf_batch>1 is worth it (and how many extra sims would compensate for any quality loss) is a separate open question — evaluate via holdout-set win-rate or direct matchups (`tournament.py`/`tools/_matchup.py`), not just games/hour or soft proxies like policy entropy. See `TARGET_MACHINE_BENCHMARK_PLAN.md` step 6.
- **Sanity-checked at this realistic scale on M1 Air** (runs/models_7x7_v2/best.pt, seed=42, tt_max_depth=-1/unlimited, tt_max_entries=20,000,000): steady-state evals/s ~18,900-19,000, mean batch ~255.4/256 (maxed out), games/hour ~40,000-55,000 (settling ~44k after the ~80s ramp-up needed for the first of 1024 concurrent games to finish). Memory flat at ~1.95-2.0GB RSS throughout (checked at 40s and again after 700+ completed games) — no runaway growth even with unlimited-depth caching. This run was terminated early (games count didn't need to reach the full target) once steady-state metrics were established, per user instruction that games don't need to play out to completion for throughput measurement.
- MPS vs CUDA numbers are NOT comparable (see TARGET_MACHINE_BENCHMARK_PLAN.md's own disclaimer) — this M1 result is a "pipeline is stable and correct at this scale" check, not a throughput baseline for the target machine.

## Trajectory diversity / temp_threshold lock-in effect (IMPORTANT finding)
- Re-ran `tools/_measure_opening_overlap.py` at production sims (`--sims 800`, 500 games, 7x7/5walls, runs/models_7x7_v2/best.pt, seed=42, parallel=256, leaf_batch=1, default `--temp-threshold 14`) — first time this diagnostic was run at production sims instead of the old sims=64 smoke-test scale.
- **Hit-rate is HIGHER at sims=800 than at sims=64 at every depth beyond ~4** (more simulations sharpens the PUCT visit distribution around the top move, so tau=1 sampling is less diverse even with the same Dirichlet noise): depth8 56.6% (vs 55% @ sims64, similar), depth10 44.7% (vs 34%), depth12 31.5% (vs 17%), depth16 13.0% (vs ~6% "noise floor" @ sims64). More sims -> less exploration diversity under a fixed noise schedule, somewhat counter-intuitively.
- **Critical mechanism discovered — "lock-in" at temp_threshold**: distinct-state count froze essentially solid right at the threshold: depth13 (last tau=1 ply) -> 383 distinct/499 games (hit-rate 23.2%); depth14 (first tau=0/argmax ply) -> 430 distinct (13.8%); depth15 -> **430 distinct, unchanged**; depth16 -> 434 distinct (13.0%, barely moved). Once temp_threshold (14) is crossed, MCTS becomes pure argmax (deterministic given identical NN weights) — so any two games that happen to reach the SAME state at ply>=temp_threshold will replay bit-identical moves for the ENTIRE REST OF THE GAME (up to max_moves=200), since there's no more Dirichlet noise/sampling to re-diverge them (residual divergence only from rare MPS batched-inference FP noise, see the "TT stress test" section above — negligible with a trained model). This is NOT a bug — it's the same tau=1/tau=0 design as train.py's Python reference (`TEMP_THRESHOLD` = 14 there too) — but the C++ port lets us quantify it precisely for the first time via this measurement.
- **Confirms the user's hypothesis**: raising `temp_threshold` should help, because it directly controls how many plies remain in the "can still diverge" (tau=1/noisy) regime before games that happen to converge get permanently frozen into identical trajectories. The ~13% of games that share a state at ply14 are not just "similar openings" — they become full-game duplicates for training-data purposes (identical states/policies/values recorded from ply14 to game end).
- **Follow-up test CONFIRMS the fix**: identical setup with `--temp-threshold 24` (all-tau1 through the tracked depth16 window, no lock-in yet). depth1-14 numbers are IDENTICAL to the temp_threshold=14 run (as expected — same seed/model, no threshold difference yet applies since default cutoff is also 14). But depth15/16 diverge dramatically since tau=1 stays active instead of freezing:
  - temp_threshold=14 (locked at ply14): depth15 hit-rate 13.8% (unchanged from depth14) -> depth16 13.0%.
  - temp_threshold=24 (still tau=1): depth15 hit-rate **7.2%** (continues decaying) -> depth16 **1.6%** (largest group only 3/499 games).
  - i.e. raising temp_threshold from 14 to 24 cuts the depth16 exact-state hit-rate by ~8x (13.0% -> 1.6%). This is decisive, direct evidence that raising `temp_threshold` substantially improves trajectory diversity and should be considered for production self-play, not just a hypothesis.
- Caveat: `Game::kOpeningTrack` caps tracking at 16 real plies, so we can only observe up to ply16. To see how far the hit-rate keeps dropping with an even higher temp_threshold (e.g. 30-40), or to directly measure full-game trajectory duplication (not just first-16-ply state collisions), `kOpeningTrack` would need to be temporarily raised (e.g. to 40-60) for a deeper follow-up measurement.
- **Recommendation**: raise `temp_threshold` above its current default of 14 (e.g. to ~24-30) for production self-play to reduce duplicate-trajectory risk in the training data — validate the resulting policy/value quality isn't hurt (e.g. via holdout eval or matchup) before committing to a new default, since more tau=1 plies also means more suboptimal/noisy moves recorded deeper into the game.
- **ACTION TAKEN**: default changed from 14 to 20 everywhere (per user decision, without a separate quality validation pass — noted as a risk to watch for in future holdout/matchup evals). Updated in: `cpp/selfplay.hpp` (`Config::temp_threshold`), `cpp/bindings.cpp` (pybind11 `py::arg("temp_threshold") = 20`), `selfplay_cpp.py` (`--temp-threshold` argparse default), `train.py` (`TEMP_THRESHOLD` constant). `benchmark_selfplay.py`'s own `_play_one_game(temp_threshold=30)` default was already 30 and is a separate/unrelated benchmark helper — left unchanged. Rebuilt `quoridor_cpp` and re-ran `tests/test_cpp_parity.py --games 20 --seed 9` (all passed, 5303 moves) after the change.

## Full C++ self-play + train cycle loop
- Neither `selfplay_cpp.py` (generates cycle_NNNN.npz via C++ engine, never trains/touches best.pt) nor `train.py --train-only` (trains on whatever's on disk + updates best.pt/checkpoint, never generates new data) does the full AlphaZero loop alone.
- `cpp_train_loop.py` alternates the two as subprocesses for N cycles: `selfplay_cpp.py --model runs/models_7x7/best.pt --out-dir runs/data_7x7 ...` then `train.py --resume --train-only --cycles 1`. Both scripts already agree on the fixed paths (`models_7x7/best.pt`, `data_7x7/*.npz`), so nothing needs to be passed between steps. Usage: `python cpp_train_loop.py --cycles 20 --games 500 --sims 400`.
- Note: `train.py`'s model/data dir paths (`MODEL_DIR="models_7x7"`, `DATA_DIR="data_7x7"`) are hardcoded constants, not CLI flags — that's why the loop script also hardcodes them rather than taking a --model-dir option.

## Console log bookkeeping (train.py)
- `_Tee`/`_start_run_log()` in `train.py` (right before `# ── Main loop`), wired into `main()`: every non-smoke-test run tees stdout+stderr to `logs/train_<YYYYMMDD_HHMMSS>.log` (`LOG_DIR = "logs"`) in addition to the console, so every run's full transcript is kept for bookkeeping alongside the structured `training_stats.csv`. Smoke-test runs intentionally skip file logging.
- Same `_Tee`/`_start_run_log()` pattern in `selfplay_cpp.py` (own independent copy, not shared/imported), writing to `logs/selfplay_<YYYYMMDD_HHMMSS>.log`. Called unconditionally right after `args = p.parse_args()` in `main()`.
- Gotcha for testing this: don't run the full `train.py` (even `--smoke-test`) to validate logging — holdout loss evaluation runs unconditionally every cycle over `HOLDOUT_SIZE=409,600` positions regardless of `--games`/`--sims`/smoke-test, so even a "tiny" smoke test takes several minutes. To validate logging behavior quickly, unit-test `train._start_run_log()`/`_Tee` directly via `python -c "import train; train._start_run_log('logs'); print(...)"` instead of running `main()`.

## max_batch sweep on M1 Air (256 vs 512 vs 1024) — bigger isn't better on this GPU
- Same production-scale config each time (runs/models_7x7/best.pt, sims=800, parallel=1024, leaf_batch=1, threads=8, 7x7/5walls, tt_max_depth=-1, tt_max_entries=20,000,000), compared during the same early ramp-up window (games_finished still 0, first ~50s) so evals/s and mean batch are apples-to-apples across runs:
  - `max_batch=256`: ~18,900-19,000 evals/s, mean batch maxed at ~255-256.
  - `max_batch=512`: ~17,000-20,000 evals/s (settling ~17,300), mean batch ~478-511 (not fully maxed but close).
  - `max_batch=1024`: only ~8,700-9,500 evals/s (roughly HALF of the 256/512 cases), mean batch ~515-525 (barely more than the 512 case achieved, despite doubling the ceiling).
- **Conclusion: on the M1 Air's integrated GPU (MPS), max_batch=1024 is functionally doable (no crash/OOM) but actively hurts throughput** — batches don't reliably get much fuller than ~520 even with headroom to 1024 (not enough concurrent pending leaves arrive within `--flush-us` to fill it), while the larger forward-pass latency per call reduces effective evals/s. max_batch=512 is roughly on par with (maybe slightly below) 256. **256-512 is the practical sweet spot on M1 Air; don't default to 1024 here.**
- Important caveat: MPS vs the target CUDA/RTX 5070 Ti machine are NOT comparable — a discrete GPU with far more compute/bandwidth headroom may well benefit from max_batch=1024+ where the M1's integrated GPU does not. Re-sweep this on the target machine rather than assuming the M1 conclusion transfers (see `TARGET_MACHINE_BENCHMARK_PLAN.md` step 4, which already plans to test max_batch up to 1024 there).
- Methodology note: this sweep incidentally validated the `selfplay_cpp.py` console logging (`logs/selfplay_*.log`) as a reliable way to capture output from a backgrounded run even when the shell redirect (`> file 2>&1 &`) buffers/loses output on SIGTERM — the `_Tee`'d log file (which flushes on every write) had the full transcript when the plain redirected file was empty.

## Periodic progress line was a lifetime average, not live (fixed)
- `selfplay_cpp.py`'s 5-second progress print used `n_evals`/`n_batches` accumulated since `t0` and never reset, so `evals/s`/`mean batch` were lifetime cumulative averages, not current activity. This caused confusing readings like "mean batch 230" when only ~2 games remained active near the end of a run (with `--parallel == --games`, finished games aren't replaced, so true instantaneous batch size collapses toward the tail, but the cumulative metric barely moved since it was dragged by tens of thousands of earlier large batches).
- Fixed: separate `win_evals`/`win_batches` counters reset to 0 after every print, so the periodic line now reports a rolling last-~5s average (`win_evals / win_elapsed`, `win_evals / win_batches`) instead of a lifetime one. The final end-of-run summary print still uses the original never-reset `n_evals`/`n_batches` (correct, since that one *should* be a whole-run total).
- Verified: `--games 400 --parallel 400 --sims 64 --max-batch 256` (all games start together, no refill) shows mean batch correctly decaying 240 → 213 → 164 → 87 → 14.6 as games finish near the end, visibly matching the real tail-off effect instead of masking it.

## C++ tournament tool (`cpp/tournament.hpp` + `TournamentManager` + `tournament_cpp.py`) — IMPLEMENTED + benchmarked
- Ports `tournament.py`'s round-robin Elo tournament (Bradley-Terry `compute_elo()` reused unchanged) to C++, mirroring the self-play architecture (worker threads never touch GIL; Python thread(s) drive `get_batch`/`put_results`).
- `TournamentManager` (cpp/tournament.hpp) supports multiple distinct models/agents with per-agent sims/temperature/c_puct/fpu_reduction, round-robin pairing, via `agent_model_ids` etc. Bound in `cpp/bindings.cpp`.
- **Critical architectural lesson**: the naive design (ONE big `TournamentManager` covering ALL pairs at once + one Python inference thread PER DISTINCT MODEL in the whole roster) causes severe GIL contention as model count grows — at 10 models (10 concurrent Python inference threads) this was measured SLOWER than Python's multiprocess `tournament.py` (900 games: only 8 done after 122s, vs Python's steady ~2.6s/game). Self-play doesn't hit this because it only ever has ONE hot model/one inference thread.
- **Fix (implemented, `tournament_cpp.py`'s `play_pair()` + rewritten `main()`)**: process the round-robin ONE PAIR AT A TIME sequentially. Each pair gets its own small `TournamentManager` scoped to just that pair's 1-2 distinct models (locally remapped ids), with `parallel_games = min(args.parallel, games_per_pair)`. This bounds concurrent Python inference threads to 1-2 at any time (matching self-play's sweet spot) while still allowing large batches within a pair.
- **IMPORTANT CAVEAT — the fix only pays off when `--games` per pair is large (100s)**: tested at `games_per_pair=20` (10-model roster, 900 total games) — no speedup, actually slower (~6-7s/game) because `parallel = min(parallel, games_per_pair)` caps out at just 20, split ~10/model, too small to amortize per-eval-call overhead. Tested at `games_per_pair=300` (single pair, best.pt vs cycle_0081.pt, sims=200, temp=1, threads=8, parallel=256, M1 Air): **C++ 286.3s total (1.0s/game) vs Python tournament.py (8 workers) extrapolated ~1040s (~3.5s/game) — a ~3.6x speedup**, confirming the tool's benefit is specific to the "few-ish models, hundreds of games per pair" regime, not small games-per-pair scans (where plain Python `tournament.py` is fine / possibly simpler).
- **Correctness validated**: best.pt vs cycle_0144.pt @ sims=400, temp=0 (deterministic) vs `tools/_matchup.py` — game 1 exact match (29 plies, same winner); game 2 same winner, different plies (38 vs 48, attributed to expected MCTS-threading tie-break nondeterminism, not a bug). `--fpu` default deliberately kept at 0.1 (differs from `MCTSAgent`'s eval default of 0.2 in mcts.py) per explicit user preference.
- **Recommendation for future use**: when running real tournaments (~10 models, want good Elo estimates), use `tournament_cpp.py` with `--games` in the hundreds per pair to get the real speedup; don't use it for quick small-games-per-pair smoke tests where the overhead of many small batches negates the benefit.
- Full production example: 100-game, temp=1, sims=800 tournament between `models_7x7/best.pt` and `models_7x7/checkpoints/cycle_0141.pt` (M1 Air) took 936.2s (9.4s/game — much slower per-game than the 300-game/sims=200 benchmark above since sims=800 costs much more per move) and gave `best.pt` a ~131 Elo edge (68.0% score, 67W-2D-31L). Note a real P1/P2 asymmetry was observed in that matchup (`best.pt` won 78% as P2 vs 56% as P1) — worth checking for in any matchup, not assumed to be symmetric.

## CPU-vs-GPU bottleneck, measured on the target machine (2026-07-25, Ryzen 7800X3D 8c/8t + RTX 5070 Ti, CUDA)
- First real CUDA measurements; supersedes all M1/MPS throughput numbers above for balance questions.
- **Inference ceiling** (real `runs/models_9x9_scratch/best.pt`, 128f/10res/gpool3, 2.9M params, 9x9, bf16, full numpy->cuda->forward->numpy round trip as `selfplay_cpp.py` does it): batch 256 → 54.5k evals/s, 512 → 84k, **768 → 93.7k, 1024 → 92.6k, 1280 → 91.6k**, 1536 → 82k, 2048 → 83k, 4096 → 85.6k, 8192 → 87.2k. **Plateau from ~768 up at ~90k evals/s — bigger batches buy nothing** and cost latency (11ms at 1024 vs 94ms at 8192, i.e. staler virtual-loss stats for everything in flight). Run-to-run variance ~10%. `--max-batch 1024` is already on the plateau; 768 is arguably better. Do NOT chase 2048+.
- **That plateau is specific to this GPU + this network, exactly like the M1 max_batch sweep above was specific to MPS.** The 5070 Ti saturates at ~90k evals/s on a 2.9M-param 128f/10res net at 9x9; time per batch grows linearly past the knee (8x the batch for 8.5x the time), i.e. it is genuine compute saturation, not launch overhead. A bigger card, or a bigger/smaller net, moves both the knee and the ceiling — re-run the scan after any architecture change or GPU change. What does transfer is the shape: once batches saturate the GPU, a larger `--max-batch` only buys latency (and staler virtual-loss stats), never throughput.
- **Production cycle is CPU-tight but the GPU is under-fed, not idle**, and the constraint moves around within a single cycle. Config: 2048 games / sims 800 / parallel 2048 / max_batch 1024 / bf16 / TT unlimited depth, 5M cap. Across a cycle, ignoring the tail: system CPU median 92% (peak 100%), GPU util median 42% (peak 85%), GPU power median 98W (peak 178W), peak RSS 13.8GB. The phases behind those medians:
  - opening burst (first ~25s): mean batch ~760, 61k evals/s, **GPU 78-85% / 167-178W**, CPU ~50% — genuinely GPU-bound.
  - then the TT starts absorbing the shared openings: mean batch collapses to ~2-30, evals/s to ~200-5k, **CPU 96-100%**, GPU 10-19% / 32-46W — CPU-bound.
  - mid/late game as games diverge: batch ~100-480, 15-47k evals/s, GPU back to 54-67%, CPU 100→71%.
  - starved tail (last ~90s, few games left): CPU 17-31%, GPU 8-15%, inference thread 60% blocked in `get_batch`. This is what `--abandon-stragglers-below` exists for; production runs 48 (now the default).
- **Why the GPU is under-fed is by design:** the great majority of a cycle's ~92M simulations never reach the net — TT hits + in-tree exact solving (~1.9-2.1M hits/cycle) + terminal nodes answer them on the CPU. At `temp_early/final/halflife = 1.0/0.2/10` that is 89.9% of ~92.5M sims (9.38M evals, 25.5k evals/s); at the sharper 0.8/0.15/6 it was 93.8% of ~93.4M (5.83M evals, 15.7k evals/s). The fraction is not a fixed property of the engine — it tracks how diverse self-play currently is, so it drifts as the policy sharpens over a run (see the diversity section below). Either way demand sits far under the ~90k evals/s ceiling.
- Conclusion for hardware: more/faster cores beat a better GPU here, but "8 cores pinned while the GPU waits" was an overstatement — README's Speed section now carries the measured medians/peaks instead.
- **Instrumentation gotcha (cost ~20min):** a child `selfplay_cpp.py`'s stdout is block-buffered through a pipe (its `_Tee` flushes only the log file), so a parent harness reading `proc.stdout` line-by-line sees NOTHING for ~10min until the 8KB pipe buffer fills — and a duration check inside that read loop never runs, so runs overshoot their window and survive as orphans after the parent is killed. Launch the child with `python -u`, put the timeout in a watchdog thread rather than the read loop, or just read `runs/logs/selfplay_*.log` (flushed every write).
- Inserting two `torch.cuda.synchronize()` calls per batch to time the inference loop's stages costs almost nothing end-to-end (19,916 vs 20,062 games/hour), so instrumenting that loop is a safe way to measure it.

## Self-play diversity collapse and the temperature-schedule fix (2026-07-25)
- Prompted by the ~90% no-NN-eval figure above. That figure is about *simulated* leaves and says nothing about recorded data, so the recorded data was counted directly (`states` rows hashed; LR-augmented second half excluded).
- **`data_9x9_scratch/cycle_0320.npz` had only 19,750 distinct positions out of 131,465 recorded (15.0%)**, with single positions repeated up to 2,000x (i.e. essentially every game in the cycle). Distinct-per-ply: ply2 **2** distinct / 2000 games, ply8 19, ply16 60, ply24 121, ply48 551 (largest group still 393 games).
- **Monotone decay across the run** (distinct rows / distinct at ply 8): cycle 20 → 66.3% / 15.8%; 100 → 41.4% / 6.7%; 200 → 36.6% / 8.9%; 280 → 24.4% / 0.9%; 320 → 15.0% / 0.9%. Not a regression from one change — a fixed temperature schedule samples ever more deterministically as the policy sharpens, so diversity bleeds away gradually.
- **Fix applied: `temp_early` 0.8→1.0, `temp_final` 0.15→0.2, `temp_halflife` 6.0→10.0**, changed in all five places that carry these defaults (`cpp/selfplay.hpp`, `cpp/bindings.cpp`, `selfplay_cpp.py`, `cpp_train_loop.py`, `train.py`). They had drifted out of sync beforehand (hpp said halflife 20.0, callers 6.0, train.py 0.9/0.15/7.0) — check all five when touching this.
- **Measured effect** (same model/config, fresh 2048-game cycle): distinct rows **15.0% → 42.1%**; ply16 5.5%→14.6%, ply24 6.0%→39.8%, ply32 15.6%→55.0%, ply48 28.0%→65.3%. **Throughput-neutral** (20,062 vs 19,916-20,554 games/hour): fewer TT hits means 61% more real NN evals (9.38M vs 5.83M/cycle, 25.5k vs 15.7k evals/s), which the idle GPU absorbed for free. Good illustration of the headroom above.
- **Still unfixed — the opening is a fixed book.** Even after the change, ply2 has 2 distinct positions (2,047 of 2,048 games share one) and ply8 only 25. Temperature isn't the cause there (tau ≈ 0.9 at ply 2): with 800 sims on a converged policy the runner-up moves sit at or below `temp_prune_visits` (4) and get pruned out of the sampling set, often leaving the argmax as the only eligible move. Root Dirichlet noise (alpha 0.3, eps 0.25) rarely flips it.
- Candidate fixes, none implemented: exempt the first few plies from `temp_prune_visits`; raise root noise for early plies; or port `train.py`'s `random_wall_plies`/`random_wall_fraction` opening randomiser — **it exists only in the Python path, the C++ self-play has no opening randomisation at all** (`grep random_wall cpp/` is empty), which is likely the single biggest lever.
- To redo this measurement: hash the `states` rows of a `cycle_NNNN.npz` and count distinct ones, skipping the LR-augmented second half (`states[n//2] == states[0]` flipped on axis 3). For per-ply numbers, segment the file back into games using `plies_to_end` — it decreases by 1 within a game and jumps up at a boundary, so absolute ply is `first_value - value`.

## Playout cap randomization (IMPLEMENTED + A/B'd + now the default, 2026-08-03)
- KataGo arXiv:1902.10565 §3.1. Each turn is drawn FULL (`pcr_full_prob`, `--sims` sims, Dirichlet noise, recorded as training data) or CHEAP (`--pcr-cheap-sims`, no noise, NOT recorded). Defaults now `0.25 / 160` in **four** places that must stay in sync — `cpp/selfplay.hpp`, `cpp/bindings.cpp`, `selfplay_cpp.py`, `cpp_train_loop.py` (same drift hazard as the temp schedule). `--pcr-full-prob 1.0` restores pre-PCR behaviour exactly (`begin_turn` returns before touching the game RNG).
- **The point is not sims-per-sample — cheap turns make that WORSE.** Vanilla: 600 playouts per recorded sample. PCR at p=0.25/(600,100): 900. What it buys is *finished games*: every position in a game shares one value target, so a game yields one independent value observation regardless of how many of its positions are recorded. 2.67x more games per unit compute is 2.67x more independent value signal. Policy targets cost 1.5x more each but stay full-strength instead of being diluted.
- Cheap turns must still be played well. Dropping to raw-policy moves would make the game outcome a bad value target for the positions that WERE recorded. 160 is 1/5 of the production 800, matching KataGo's annealed (1000,200). **`pcr_cheap_sims` is absolute, not a fraction of `--sims` — re-tune it if `--sims` changes.**
- Recorded rows go sparse, so `plies`/`plies_to_end`/ply stats now track **real game plies** separately from recorded rows (`rec_ply[]`). Verified ratio 1.00 with PCR off, exactly 4.00 at p=0.25, game length unchanged (~70 plies both ways). The game-segmentation procedure in the diversity section still works.
- Solved endgame PVs are subsampled at the same rate. They are exact and free, but also perfectly outcome-correlated, and recording 100% of endgames against 25% of midgames would skew the data toward endgames purely as a side effect of enabling PCR.
- **Throughput, production config (2048 games, 800 sims, same seed/model):** control 2000 games in 265.8s (27,090 games/hr, 124,086 positions); PCR 113.4s (63,488 games/hr, 33,032 positions). **2.34x games/hour, 2.51x fewer sims, 3.76x fewer recorded positions**, split on target at 24.8%.
- **PCR shifts the P1 win rate up ~+9 points and this is NOT a bug** (cost ~1h to establish). Relative to a null cell (PCR on, `cheap_sims=800 --pcr-cheap-noise`, i.e. gameplay identical to control) at 50.1%: suppressing noise alone +6.5, weak cheap search alone +8.5, both together only +9.1 — **strongly sub-additive, they saturate**. Control 49.7%. Measured over 3 seeds x 512 games; within-config sd ~2.2pt, which matches the nominal binomial SE, so game-level correlation does NOT inflate win-rate variance (it does inflate position-diversity numbers — don't conflate the two). Always include the null cell before decomposing.
- **A/B, 60 cycles per arm from a shared cycle_0159 start, warm-seeded with data cycles 0130-0159 so the buffer is full from cycle 1** (a cold empty buffer regressed loss 1.18 -> 1.38 in 6 cycles and would have starved the PCR arm ~4x harder, since it records 3.76x fewer positions/cycle):
  - control 5.91h (260s selfplay + 95s train per cycle); PCR **3.12h** (122s + 55s, train decaying as control-sized seeded data is displaced). **1.89x less wall-clock.**
  - Elo @ sims=100: PCR 1595.5 vs control 1565.8, head-to-head 54.7% (+/-1.6%, 1000 games) = **+29.7 Elo**. Both beat the cycle_0159 anchor (79.1% / 81.0%), so both arms were healthy.
  - **Elo @ sims=800 (the training budget): 51.2% vs 48.8%, z=+0.61, +8.7 Elo — not significant.** The sims=100 win is largely a low-search-budget artifact; 75% of PCR's self-play is *played* at 160 sims, so its net over-indexes on the low-budget regime. **Evaluate at the training sim budget, not the cheap tournament default of 100.**
  - Honest read: **equal strength at the training budget for 1.89x less compute** (95% CI at sims=800 spans ~-19 to +36 Elo). Adopted on the inference that a tie at matched cycles plus half-price cycles wins at matched compute — ~114 PCR cycles fit in control's 5.91h. **That equal-compute run was NOT performed.**
  - Raw loss is not comparable across arms: PCR 1.589 vs control 1.408 at cycle 220, while value_accuracy is identical (0.8520 vs 0.8506). Less redundant data fits worse at equal quality.
- **Diversity:** PCR's retained positions are 71.1% distinct vs control's 56.4% (cycle 190). But control produces more distinct positions per second (297 vs 189) — PCR does not win on unique-data throughput. Both arms ran `--games 2048`, i.e. the same ~2000 independent game outcomes per cycle; PCR just bought them at half price. Games, not positions, are the unit.
